# 01 · 开源方案调研：B 站视频批量转逐字稿

> 调研时间：2026-07 · 目标：找到**免费、开源**、可批量处理 B 站视频并生成文字逐字稿的解决方案，
> 并评估其与我们两个业务场景（飞书机器人、管理后台）及后续 AI 知识提炼的适配度。

## 1. 需求拆解

一条视频链接要变成"可复用的开发知识"，完整链路是：

```
B 站链接 → 解析视频信息 → 获取逐字稿 → （可选）关键帧截图 → AI 提炼 → 知识库落盘
```

其中**获取逐字稿**有两条技术路线：

- **路线 A：字幕直抓** —— 很多 B 站视频已有 UP 主上传的 CC 字幕或 B 站官方 AI 生成字幕，
  通过公开接口可直接拿到带时间戳的 JSON 字幕，**秒级完成、零算力消耗**。
- **路线 B：ASR 转写** —— 下载视频音频，用本地语音识别模型（Whisper 系）转写。
  覆盖率 100%，但批量场景下耗时和算力成本显著。

结论先行：**A 优先、B 兜底**是批量场景下的最优组合（已与需求方确认）。

## 2. 一体化开源项目盘点

### 2.1 BiliNote ⭐ 最接近需求的参考实现

- 仓库：<https://github.com/JefferyHcool/BiliNote>（MIT License）
- 技术栈：**FastAPI + Python** 后端，SQLite 存储，React 前端，提供完整 HTTP API
- 能力：
  - 支持 B 站 / YouTube / 抖音 / 快手 / 本地视频
  - 转写引擎可选：Fast-Whisper（本地，支持 GPU）、MLX-Whisper（Apple Silicon）、
    Groq（在线）、必剪/快手（在线）
  - **自动截取视频截图并插入笔记**（截图存 `/backend/static/screenshots/`）——正好对应"图片+文字稿"需求
  - 生成带时间戳跳转链接的 Markdown 笔记，任务记录与历史回看
  - Docker 一键部署（`ghcr.io/jefferyhcool/bilinote:latest`），另有桌面客户端
- 评价：功能覆盖度最高，其"下载 → 转写 → 截图 → LLM 生成笔记"的流水线设计
  与我们的目标架构高度一致。**即使自研，也应把它作为主要参考实现。**
- 局限：无飞书接入；"知识提炼"只做到单视频笔记层面，没有跨视频的知识库沉淀；
  字幕直抓仅对 YouTube 生效，B 站视频一律走 ASR（浪费算力）。

### 2.2 bili2text

- 仓库：<https://github.com/lanbinleo/bili2text>
- 输入链接一步到位：下载视频 → 提取音频 → 分割音频 → Whisper 转写
- 评价：CLI 小工具，流程清晰适合借鉴，但无服务化能力、无字幕直抓、无截图。

### 2.3 BiliSpeech2Text

- 仓库：<https://github.com/Frewen/BiliSpeech2Text>
- 与 bili2text 类似的自动化脚本（下载 → 抽音频 → 分段 → Whisper）。
- 评价：同上，可作流程参考。

### 2.4 stt（jianchang512/stt）

- 仓库：<https://github.com/jianchang512/stt>
- 定位：**离线本地"音视频 → 字幕"服务**，基于 faster-whisper，输出 json / srt / 纯文本，
  自带 Web 界面和 API 接口。
- 评价：不处理 B 站链接（只吃本地文件），但可以作为独立部署的"转写微服务"，
  我们的 pipeline 通过 HTTP 调它做 ASR 兜底。是"自研但少写代码"的一个可选组件。

### 2.5 AI-Video-Transcriber

- 仓库：<https://github.com/wendy7756/AI-Video-Transcriber>
- 多平台视频转写 + AI 摘要，开源。
- 评价：功能与 BiliNote 重叠，社区活跃度与文档均弱于 BiliNote，不作首选。

## 3. 组件级方案（自研 pipeline 的积木）

### 3.1 字幕直抓（路线 A 核心）

- **接口文档**：[bilibili-API-collect](https://github.com/SocialSisterYi/bilibili-API-collect)
  （B 站 API 逆向文档集，社区事实标准），字幕相关见
  [player 文档](https://socialsisteryi.github.io/bilibili-API-collect/docs/video/player.html)
- **Python SDK**：[Nemo2011/bilibili-api](https://github.com/Nemo2011/bilibili-api)
  （`pip install bilibili-api-python`），封装了视频信息、字幕等常用接口
- 调用链：
  1. `BV号 → aid/cid`：`GET https://api.bilibili.com/x/web-interface/view?bvid={bvid}`
  2. 拉字幕列表：`GET https://api.bilibili.com/x/player/wbi/v2?aid={aid}&cid={cid}`，
     响应 `data.subtitle.subtitles[]` 中每项含 `subtitle_url`（JSON 格式带时间戳字幕）；
     `lan == "ai-zh"` 即 B 站 AI 自动生成字幕
  3. 下载 `subtitle_url` 得到 `[{from, to, content}, ...]`，拼装成逐字稿
- ⚠️ **关键限制**（已核实，见 [bilibili-API-collect#778](https://github.com/SocialSisterYi/bilibili-API-collect/issues/778)）：
  - **未登录状态下 `subtitle_url` 大概率为空**，抓 AI 字幕需要在请求头带登录 Cookie（`SESSDATA`）
  - 接口有 wbi 签名与风控，批量请求需控制频率（建议加随机间隔、单账号日请求量控制）

### 3.2 视频/音频下载（路线 B 前置）

| 工具 | 特点 | 结论 |
| --- | --- | --- |
| [BBDown](https://github.com/nilaoda/BBDown) | B 站专用，功能最全（字幕、番剧、合集、大会员流），.NET 单文件 | B 站场景首选 |
| [yt-dlp](https://github.com/yt-dlp/yt-dlp) | 通用下载器，支持 B 站（音视频分离流需合并），`-x` 可只抽音频 | 备选；未来扩展 YouTube 等平台时复用 |

我们只需要音频（转写用），两者都支持"仅下载音频流"，可显著降低带宽与磁盘占用。

### 3.3 本地 ASR 引擎（路线 B 核心）

| 引擎 | 特点 |
| --- | --- |
| [faster-whisper](https://github.com/SYSTRAN/faster-whisper) | Whisper 的 CTranslate2 重实现，CPU 可跑（small/medium），GPU 更快；社区生态最好，BiliNote / stt 均用它 |
| [whisper.cpp](https://github.com/ggerganov/whisper.cpp) | 纯 C/C++，低资源设备友好 |
| [FunASR](https://github.com/modelscope/FunASR)（阿里达摩院） | Paraformer 中文模型，**中文识别准确率普遍优于 Whisper**，自带标点恢复，CPU 推理快 |

建议：默认 **faster-whisper（small/medium, int8）**，生态与文档最好；
若实测中文课程识别质量不满意，切换 **FunASR Paraformer**（架构上做成可插拔引擎）。

### 3.4 关键帧截图

`ffmpeg` 按字幕段落时间戳抽帧即可（`ffmpeg -ss {ts} -i video -frames:v 1 out.jpg`），
BiliNote 的截图模块可直接参考。注意：**截图需要下载视频流**（字幕直抓路线默认不下载视频，
仅当任务勾选"生成图文稿"时才追加下载）。

## 4. 方案对比与选型结论

| 方案 | 逐字稿 | 批量 | 截图图文稿 | 飞书接入 | 知识提炼 | 改造成本 |
| --- | --- | --- | --- | --- | --- | --- |
| 直接部署 BiliNote | ✅ ASR | ⚠️ 逐个提交 | ✅ | ❌ 需外挂 | ⚠️ 单视频笔记 | 二开受上游约束 |
| bili2text / BiliSpeech2Text | ✅ ASR | ⚠️ 脚本级 | ❌ | ❌ | ❌ | 仅够参考 |
| stt 作转写微服务 | ✅ ASR | ✅ API | ❌ | ❌ | ❌ | 只解决一环 |
| **自研 pipeline（选定）** | ✅ 字幕优先+ASR 兜底 | ✅ 任务队列 | ✅ ffmpeg | ✅ 原生设计 | ✅ 原生设计 | 可控，组件全部开源现成 |

**结论**：自研一个组件化 pipeline（详见 [02-架构设计](02-架构设计.md)），理由：

1. **字幕直抓**是批量场景下最大的降本点，现有一体化项目都没做（B 站方向）；
2. 飞书机器人和"跨视频知识库沉淀"是我们的核心差异化需求，任何现成项目都要大改；
3. 自研并不等于从零造轮子——下载（BBDown/yt-dlp）、转写（faster-whisper）、
   接口（bilibili-api）、截图（ffmpeg）全部是成熟开源组件，我们只写编排层；
4. BiliNote（MIT）作为参考实现，其转写与截图模块的做法可直接借鉴。

## 5. 合规与风险提示

- 逐字稿与截图仅限**团队内部学习研究**使用，不得对外传播或商用，尊重 UP 主著作权；
- B 站接口有风控：需要配置一个普通账号的 `SESSDATA`，控制请求频率（建议 ≥3s 间隔 + 抖动），
  避免账号异常；社区有"高频请求后字幕接口暂时失效"的报告（[bilibili-api#696](https://github.com/Nemo2011/bilibili-api/issues/696)）；
- B 站接口属逆向接口，可能随时变更——字幕抓取模块要有失败降级（自动落到 ASR 兜底）。
